# Vercel migration

This is the same BMO inventory UI packaged as a static page plus one Vercel
Node.js Function, using persistent Neon Postgres. It has no Cloudflare or
ChatGPT runtime dependency. The existing Sites app remains available while the
Vercel version is tried.

## Live deployment

https://bmo-fridge-buddy.vercel.app/fridge

Deployed on November 15, 2026 to Vercel Hobby with a Neon free-plan database.
The function and database use the iad1 US East region. App secrets are stored
as Vercel production secrets. This app uses its own owner password, not the
Vercel account password. The initial generated password is saved locally in
ignored `.vercel/owner-password.txt`; it is not stored in GitHub.

Live verification passed: anonymous inventory access denied, owner sign-in,
save to Neon, persistence after reload, edit, remove one, remove batch, sign-out,
on-demand scanner loading, and layouts at 360, 390, 768 and 1280px. The test
batch was removed afterward. Existing Sites/Pi inventory was not imported.

One local-to-production sample measured a 597ms page HTTP response and three
authenticated status requests at 79ms, 67ms and 69ms. These are round-trip
samples, not full page-load timings or a controlled cold-start benchmark.
Physical phone-camera scanning and Pi-to-cloud telemetry are still unverified.

Deployment installs production dependencies only. `.vercelignore` excludes
local environment files, test results, dependency folders, and `.vercel` state.

## Deploy

1. Connect Vercel to this workspace/account, then create/import a project with
   root directory `vercel-app`. Framework preset: Other. The checked-in
   vercel.json sets the build command, static directory, API routing, and iad1
   function region.
2. Add Neon Postgres through the Vercel Marketplace and connect it to the
   project. Select a nearby US East region to reduce API/database round trips.
   Vercel supplies DATABASE_URL. Preview and production should use separate
   databases when testing destructive workflows.
3. Set these server-only environment variables (never NEXT_PUBLIC_):
   - DATABASE_URL: Postgres connection URL from the database integration.
   - BMO_OWNER_PASSWORD_HASH: scrypt digest generated by scripts/configure.py.
   - BMO_SESSION_SECRET: random session signing key generated by that script.
   - BMO_DEVICE_TOKEN: separate random sensor-upload token from that script.
4. Pull configuration into an ignored .env.local file and run `npm run
   db:migrate` before deployment. This creates the schema without deleting
   existing data. The build does not run database migrations.
5. Deploy to Vercel, verify sign-in and inventory persistence, and measure the
   live API's first request and subsequent request latency. Do not claim live
   performance based on local timing. Existing Sites inventory is not copied
   automatically; retain the old app until data transfer is confirmed.

Run `python scripts/configure.py` locally to create an ignored .env.local with
an owner password hash and separate secrets. It prompts for the password with
input hidden and never prints credentials. Keep the file out of Git. Copy its
values through Vercel's secret environment-variable controls; never paste them
into chat, screenshots, client JavaScript, or shell commands.

The private owner sign-in uses a hashed password, signed HttpOnly/Secure cookie,
SameSite=Strict, origin checks, and a Postgres-backed sign-in attempt limit.
Unauthenticated visitors can see only the sign-in form. Food APIs require the
owner session; the Pi's token grants only POST /api/readings. A public recruiter
demo should use a separate sample database or browser-local data.

## Validation

- `npm ci`
- `npm test` runs the actual queries against PostgreSQL in PGlite, without a
  hosted database. It covers inventory, expiration batches, sign-in, cookies,
  rate limiting, identity spoofing, device uploads, and stale temperature data.
- `npm run build` checks syntax and required assets.
- `node scripts/mobile-check.mjs` uses installed Edge to test the UI with local
  PostgreSQL test data at 360, 390, 768 and 1280px. It covers sign-in, manual
  add, editing, removal, search, QR form filling, and sign-out. Screenshots go
  to ignored test-results/. These are browser simulations, not physical-phone
  camera validation.

The scanner library loads only when scanning starts, saving about 395 kB from
the initial page's script downloads. Temperature/history refreshes stop while
the page is hidden or signed out. Product lookup can still wait for the external
Open Food Facts service; manual entry remains available.

## Pi uploader

The existing ../cloud_uploader.py supports this deployment using BMO_CLOUD_URL
and BMO_DEVICE_TOKEN in the Pi's private .env.cloud file. For the Sites version,
keep using BMO_SITES_SERVICE_TOKEN instead. Use only one token type. Run a
one-shot test first, then enable the existing cloud uploader service template.

## Data migration

Existing inventory stays in the old app until exported and imported. Export
its /api/inventory JSON while signed in and save it to an ignored local file.
With .env.local configured for the new database, run:

```
node --env-file=.env.local scripts/import-inventory.mjs <inventory-json-file>
```

The import validates input and inserts all batches in one transaction. It
refuses a nonempty destination inventory to prevent accidental double imports.
Use a fresh database; it never clears existing food. Verify the imported count
before switching the link used on your phone. Temperature history is not
transferred by this inventory importer.
